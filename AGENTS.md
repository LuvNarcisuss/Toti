# Toti music iOS application

- Music social application adapted from build-teto-social-ios. Five tabs Lounge / Voice / Notebook / Chats / Me. Live and Shorts are retired. No Phrases routes or teaching features.
- iOS 16+, Swift 5, UIKit, AVFoundation. No SwiftUI, Objective-C, Flutter or React Native.
- Product Toti, target/scheme toti, Bundle ID com.toti.music (local identifier; registration unconfirmed). Configuration source TotiMusic/project.yml.
- Repository rules, README and docs live at the repository root. Xcode project, source, configuration, tests and scripts remain under TotiMusic/; resource URL manifests remain under TotiMusic/Configuration/. Assets/ is an ignored local archive; builds fetch verified HTTPS resources into DerivedData. Application-relative paths in technical or historical documents refer to TotiMusic/ unless stated otherwise.
- Read docs/music-community-redesign.md for the approved current feature design, and README.md for verification status. docs/template-baseline is historical material, not current brand/media/configuration.
- All app-owned visible text is English. No demonstration labels or fabricated online activity.
- Warm cream/plum/coral design. Own icons are generated transparent bitmaps via TotiIcon, not system symbols. Portraits use sourced real photography.
- Bundled photography must retain credits and license evidence. Portrait subjects are not represented as actual app accounts or endorsers. Retired video assets stay outside the app target.
- Keep stable IDs and atomic persistence. isDance, danceCategory, savedDemoVideoIDs and legacy Phrase models are compatibility fields; do not expose Phrases or erase private data.
- Diamonds only. Ordinary messages/comments are free. No fake payment success or starting credit. Configure owned products in TotiIdentity.
- No build, typecheck, app launch, Simulator, Preview or tests without explicit user authorization. Authorization to run tests includes the build, Simulator, installation and launch steps required below. Static file/resource/configuration checks and XcodeGen metadata generation are permitted.
- Every test run must use the **Toti UI Acceptance** simulator. Before testing, build the latest Toti from the current working tree, install that build on this simulator, and launch it; select this same simulator explicitly for simulator-based test destinations. After testing, ensure this latest build is running on Toti UI Acceptance. If the simulator is unavailable or any required step fails, report the blocker instead of substituting another simulator or an older build.
- Report exact service gaps and verification scope. No signing or deployment credentials are included.

## Approved backend migration

- The selected backend is the dedicated Toti Supabase project `gjodhvpzkdnxdjmorjfw` in `ap-southeast-1`; do not reuse Bibi or another application's settings. Read `docs/backend/contract.md`, `docs/backend/release-checklist.md` and the deployment record before backend changes.
- One-tap Supabase anonymous guest sign-in is the chosen authentication method as of 2026-10-28; it supersedes email OTP and removes SMTP as a login dependency. Guest sessions persist in Keychain; logout or session loss cannot recover an unlinked guest. Profiles, text Lounge, private Notebook, relationships/reports, text chats/groups and room membership/text are the initial online scope. RTC and server-verified purchases remain separately unavailable. Photo/avatar transfer uses authenticated JPEG validation, private immutable revisions and actual trusted SQL review. Pending/rejected media is owner-only; normal uploads remain pending until an operator actually reviews them. Preserve the last approved avatar during replacement review. See docs/backend/media-acceptance.md and media-backend-implementation.md.
- `usesOnlineBackend=true` and `rolloutEnabled=true` select the user-requested guest integration build. This is not production acceptance. The online path uses real guest identities and never falls back to authored accounts or local business success.
- Preserve `Application Support/Toti` independently. Online code uses `TotiOnline`, and archive reads must not invoke legacy migration or cleanup. Upload private items only after individual consent; never promote old wallet credits.
- Cloud account deletion is authorized only for the authenticated caller's own account and associated owned containers/data. The deployed Edge Function has no arbitrary-account or operator HTTP route. Preserve the local archive and original Photos files.
- The existing no-build/no-test rule still applies. Deployment and static inspection do not constitute online flow acceptance.

- Entry design (2026-10-28): every cold launch shows the original EntryController welcome, then login, even when a guest session is saved. Only explicit Log in opens the tabs; reuse the stored guest without signing it out, deleting it or creating a replacement. Reopening from background does not restart entry. Reuse the original welcome/login artwork and layout. Login has one Log in action, one agreement sentence with a checkbox and inline online PDF links. Unchecked login opens Agree and continue / Disagree confirmation; accepted login uses real guest authentication. Keep agreement URLs and byte hashes in TotiIdentity, and use the shared PDF reader in Login and Settings.

- Simulator authentication requires a signed app: preserve simulator-only ad-hoc signing in project.yml and never install an unsigned CODE_SIGNING_ALLOWED=NO build for runtime acceptance. Live guest tests require explicit disposable-data authorization and TOTI_LIVE_GUEST_ACCEPTANCE=1. Their Debug-only UUID override isolates Keychain, journals and the non-user-consent test marker from real sessions; Release ignores it.

- Original artwork and prompts are restored only as clearly labeled Toti editorial content, with illustrative-photo disclosure and no fictional member identities or engagement. Private archive photo copying requires review and consent for each individual item and creates a private draft. Live image acceptance uses generated pixels only, isolated guests and explicit cloud-fixture authorization.
